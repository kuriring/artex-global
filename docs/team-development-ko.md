# ARTEX 팀용 포크 개발 계획

기준일: 2026-11-02. 목표는 2027년 레드팀 업무에서 사용할 단일 팀의 사내 설치형 플랫폼이다.
외부 고객에게 제공하는 다중 조직 SaaS는 초기 범위에 포함하지 않는다.

이 문서는 구현 계획이다. 현재 포크에 사용자별 계정, 역할별 권한, 프로젝트 접근 격리가 구현됐다는 의미가 아니다.

## 1. 포크와 상류

- 팀 저장소: `kuriring/artex-global`
- 직접 상류: `jiwoochris/artex-global`
- 검토 기준 커밋: `fdfb7a17b7da5e2de716c0e98475ec77a41c64c6`
- `origin`은 팀 저장소, `upstream`은 직접 상류로 설정한다.
- 기존 Go 모듈 경로와 에이전트 프롬프트는 유지해 상류 변경을 비교하기 쉽게 한다.
- 기존 [LICENSE](../LICENSE), 저작권 표시와 원본 문서를 유지한다.

상류의 [유지보수 문서](../MAINTAINING.en.md)는 원본 `Autumn-27/ARTEX`와의 동기화를 설명한다.
이 팀 포크에서는 우선 `jiwoochris/artex-global`을 추적한다. GitHub CLI를 사용할 때는
`--repo kuriring/artex-global`을 명시해 상류에 PR이나 릴리스를 잘못 만들지 않도록 한다.

## 2. 코드에서 확인한 재사용 기능

| 기능 | 근거 | 팀 개발 방향 |
| --- | --- | --- |
| 목표·계획·Worker 실행과 작업 상태 | [engine](../server/engine.go), [manager](../server/manager.go) | 기존 실행 흐름 재사용 |
| 자산·회사·작업·탐색 그래프 | [schema](../db/schema.sql) | 분류 데이터와 사용자 접근 권한을 구분 |
| 재검증 이력·원본 스냅샷 | [DB](../db/finding_retests.go), [API](../server/finding_retests.go) | 재구현하지 않고 프로젝트 접근 제어 연결 |
| 증적과 트래픽 연결 | [설계 문서](finding-traffic-evidence-ko.md) | 파일·다운로드·내보내기에도 권한 적용 |
| 작업별 실시간 이벤트 | [broadcast](../server/broadcast.go) | 구독 시와 권한 회수 시 사용자 권한 확인 |
| 공유 관리자 로그인 | [auth](../server/auth.go) | 사용자 식별자와 세션 관리 도입 |

회사별 자산이나 작업 분류가 있다는 사실만으로 사용자 간 접근 격리가 보장되지는 않는다.
현재 로그인은 `ARTEX` 고정 사용자이며, JWT subject 역시 고정되어 있다.

## 3. 이번 부트스트랩의 변경

1. 바이너리 자체 업데이트 소스를 `kuriring/artex-global`로 고정한다.
2. 향후 릴리스 이미지 발행 경로를 `ghcr.io/kuriring/artex-global`로 변경한다.
3. 명시적인 팀 이미지가 없으면 실행 구성이 실패하는 Compose override를 추가한다.
4. 기존 기능과 미구현 팀 기능을 구분해 개발 순서와 완료 기준을 기록한다.

이 변경 자체는 릴리스나 이미지를 발행하지 않는다. 첫 팀 릴리스 이전에는 앱 내 업데이트 조회가
릴리스 없음 오류를 반환할 수 있다. 상류의 예전 릴리스 자산은 팀 수정 사항을 포함하지 않는다.
컨테이너 업데이트는 새 이미지로 재배포하는 방식을 사용한다.

## 4. 팀 이미지 실행

기본 [docker-compose.yml](../docker-compose.yml)은 상류 이미지를 유지한다.
소스 코드만 수정하고 기본 Compose를 실행하면 수정한 코드가 실행되는 것이 아니다.

팀 이미지가 준비된 뒤 `.env`에 `POSTGRES_PASSWORD`와 `ARTEX_TEAM_IMAGE`를 설정한다.
`ARTEX_TEAM_IMAGE`는 실제로 빌드한 로컬 태그 또는 발행한 전체 이미지 태그/digest이다.
`ARTEX_TAG`는 기본 Compose의 상류 이미지 태그용이며 팀 override에는 적용되지 않는다.

```bash
docker compose -f docker-compose.yml -f docker-compose.team.yml config --quiet
docker compose -f docker-compose.yml -f docker-compose.team.yml up -d
```

로컬 팀 이미지가 필요한 경우, Node.js 22 이상·저장소가 요구하는 Go·Docker를 준비한 뒤
저장소 루트에서 다음처럼 빌드할 수 있다. 예시는 Linux arm64 이미지용이다.
amd64 서버용으로 만들려면 `GOARCH`, 출력 디렉터리, `--platform`을 모두 amd64로 맞춘다.

```bash
(cd web && npm ci --include=dev && npm run build:static)
mkdir -p server/webui/dist dist/arm64
cp -R web/out/. server/webui/dist/
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -tags embedui -o dist/arm64/artex ./cmd/artex
docker build --platform linux/arm64 -t artex-team:local .
```

이때 `.env`의 팀 이미지 값은 `ARTEX_TEAM_IMAGE=artex-team:local`이다.
공유 환경에는 검증한 버전 또는 digest를 고정하고 이전 이미지·DB 백업의 복구 절차를 함께 관리한다.
기본 loopback 바인딩과 최초 관리자 설정 토큰은 유지된다.

## 5. 구현 순서

### 단계 0: 재현 가능한 기준선

- 백엔드 빌드, 단위 테스트, 프런트엔드 정적 빌드 결과를 기록한다.
- PostgreSQL 통합 테스트는 기존 CI처럼 패키지별 독립 DB에서 실행한다.
- Go 모듈 캐시에서 `norma`를 확보할 수 있는지 검증한다. 원본 GitHub 접근 불가와 모듈 다운로드 실패를 혼동하지 않는다.
- 실행 도구와 브라우저 패키지 버전을 고정하고, 검증한 컨테이너를 팀 명의로 발행한다.
- 완료 기준: 다른 개발 환경에서 동일 커밋을 빌드하고 로그인 화면을 열 수 있다.

### 단계 1: 사용자·프로젝트 권한

초기 제안은 한 설치에 한 팀, 팀 아래 여러 프로젝트이다. `company`는 대상 조직 정보로 유지하며,
프로젝트는 접근 권한과 수행 기간을 묶는 별도 단위로 둔다.

도입할 데이터 모델:

- `users`: 사용자 식별자, 상태, 인증 정보 또는 외부 인증 주체.
- `projects`: 이름, 상태, 생성자.
- `project_members`: 프로젝트별 사용자와 역할.
- `sessions`: 만료·취소 가능한 사용자 세션 또는 이에 준하는 세션 버전 관리.
- `audit_events`: 행위자·프로젝트·행위·대상·성공/실패·시간. 비밀번호나 API 키 원문은 저장하지 않는다.

역할 초안:

| 역할 | 범위 |
| --- | --- |
| 관리자 | 사용자·프로젝트·연결 설정·실행 환경 관리 |
| 수행자 | 배정된 프로젝트에서 작업 생성·실행·중지·재점검 |
| 검토자 | 배정된 프로젝트의 결과 열람·판정·보고서 검토; 도구 실행 불가 |
| 열람자 | 배정된 프로젝트의 허용된 결과 조회 |

새 API를 만들기 전에 기존 경로를 모두 목록화하고 기본 거부 정책을 적용한다.
관리 API는 관리자만 사용하고 프로젝트 API는 서버가 실제 소유 관계와 멤버십을 확인한다.
화면의 버튼을 숨기는 것으로 권한 검사를 대신하지 않는다.

전환 시 기존 데이터는 관리자 전용 기본 프로젝트에 귀속한다. 기존 공용 JWT는 전환 시 무효화하며,
복원 가능한 백업을 만든 뒤 마이그레이션한다. 공용 로그인 경로를 우회 수단으로 남기지 않는다.
로컬 계정 또는 OIDC 선택은 팀의 기존 인증 환경을 확인해 확정한다.

완료 기준:

- 서로 다른 프로젝트의 두 사용자가 ID를 바꿔 요청해도 작업·자산·증적·트래픽·보고서가 노출되지 않는다.
- 목록·검색·다운로드·내보내기·SSE·재검증 등 보조 경로도 같은 권한 규칙을 적용한다.
- 공유 자산 저장소, Workspace 파일, LLM 기록, Agent의 도구 호출과 메모리 검색도 프로젝트 경계를 지킨다.
- 실행 중인 작업에는 프로젝트 및 실행 주체가 연결되고, 권한 회수 시 후속 실행·이벤트 구독의 처리 규칙이 적용된다.
- 검토자·열람자는 실행/중지/설정 변경 API를 직접 호출해도 거부된다.
- 성공·실패한 중요한 변경을 실제 사용자 기준으로 감사 기록에서 추적할 수 있다.

### 단계 2: 실행 환경과 복구

- 콘솔/API 서버와 실행 Runner를 분리한다.
- 프로젝트별 실행 디렉터리, 네트워크 범위, 자격 증명 접근을 분리한다.
- 실행 전 범위를 검사하고 시간·요청 수·비용 상한과 중지 동작을 적용한다.
- 재시작 후 작업 상태를 복구하되 완료 여부가 불명확한 작업을 자동 중복 실행하지 않는다.
- 완료 기준: 한 작업의 실패·중지·재시작이 다른 프로젝트 실행과 증적을 훼손하지 않는다.

### 단계 3: 실무 평가 품질

- 기존 재검증 기능에 담당자 판정과 조치 전후 비교를 연결한다.
- 한 종류의 EDR/SIEM부터 실행 기록과 이벤트를 연결한다.
- 실행 실패, 로그 없음, 수집 미확인, 경보 없음, 경보 확인을 별도 상태로 표시한다.
- 완료 기준: 소유한 테스트 환경의 점검 → 증적 검토 → 수정 → 재점검 흐름을 반복할 수 있다.

## 6. 변경 검증과 공개 저장소 운영

관련 [기여 절차](../CONTRIBUTING.en.md)를 따르고 상류 프롬프트 및 원문을 보존한다.
이 포크는 공개 저장소이므로 실제 대상·고객명·자격 증명·스캔 결과·증적은 커밋과 공개 이슈에 넣지 않는다.
일반적인 기능 코드와 합성 테스트 데이터만 게시한다.

단계 1의 인증·권한 변경은 API 부정 테스트와 PostgreSQL 통합 테스트를 포함한다.
DB 없는 테스트 실행에서 통합 테스트가 건너뛰어졌다면 이를 통과로 기록하지 않는다.
단계 0의 전체 환경 검증과 이후 기능의 완료 기준은 별도로 기록한다.

## 7. 부트스트랩 검증 기록

2026-11-02, macOS arm64에서 Go 1.26.3 도구체인과 `norma v0.4.3`을 다운로드해 확인했다.

- `go build ./...`: 통과.
- `go vet ./agent/ ./selfupdate/`: 통과.
- `go test ./selfupdate ./agent -count=1`: 각 패키지 통과. 에이전트 테스트는 로컬 HTTP 테스트 서버를 열 수 있는 환경에서 실행했다.
- `python3 -I scripts/check-doc-links.py`: 통과.
- `git diff --cached --check`: 통과.
- Compose 설정: 팀 이미지 지정 시 해당 이미지 선택, 미지정 시 명시적인 오류로 거부됨을 확인.

PostgreSQL 통합 테스트는 DB 미설정으로 실행하지 않았다. 프런트엔드 정적 빌드,
컨테이너 이미지 빌드·발행, 실제 점검 실행도 이 검증에 포함되지 않는다.
따라서 위 결과는 단계 0 전체 완료나 팀 서비스 배포 완료를 의미하지 않는다.
